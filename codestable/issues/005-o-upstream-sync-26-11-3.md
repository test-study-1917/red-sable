### Sticky TTL 验收

修补沿用 SableClient SDK 的 `f6dc480` 基线，由本仓库的 [Cargo 补丁](../../vendor/sable-matrix-sdk/UPSTREAM.md) 自动接入。独立轮询和 SDK 都识别稳定和已部署的字段；SDK 在 typed HTTP 响应就绪、等待 outgoing E2EE 之前记录时间。房间在同一把锁下读取未过期项和近期显式截止记录，名单按事件 ID 校准。Widget 和邀请继续读取活跃项。

原基线的两个失败场景已接入常驻回归，不需要手工应用补丁：

```sh
cargo test --locked -p sable-core --lib -- sticky_ttl_primary_acceptance
```

- 对早发 10 秒、剩余 TTL 为 1 秒的成员，SDK 和独立轮询分别以各自收包时刻校验：+999 ms 可见，+1000 ms 不可见。另注入早于处理时刻的收包时间，验证延迟处理不重启计时。
- 独立轮询先录入较晚截止的事件，SDK 收到零 TTL 或较短正 TTL；首次合并安排在 SDK 截止后，必须撤下同 ID 的旧条目，保留同键不同 ID 的新条目。

本次 220 项通话测试通过（含上述回归），开发版 WASM 和 Vite 静态站点构建通过。

相邻场景与验证边界：

- 活跃通话的独立轮询在解密前将显式截止交给共享名单。同一 Megolm 事件先成功加入、再从独立轮询收到零 TTL 的完整时序尚无专门的运行回归。
- 解密返回时需核对房间 sticky 代次，并在提交锁内使用同 ID 当前的有效截止。截止来源取自收包外层，不从解密后改写的 TTL 字段判断；显式 TTL 优先于推算值，显式值之间取较早截止。回归覆盖解密途中收到零 TTL，也覆盖后来收到显式正 TTL、截止晚于旧推算值时的成功录入和失败重新排队。
- 显式 TTL 纠正较早推算时，`Reader` 只撤销或更新由推算到期产生的暂定退场，保留已验证缺席和合法离会。回归覆盖未同步时先记下推算到期、再改用较晚显式截止、两次截止都过去后才恢复同步的顺序，并验证排队 end 在最终容差内外的结果。
- 结束事件和排队重试在最终认领锁内重读本地 sticky 证据并校准截止；不在锁内请求 `/members`，不从未验证缓存新增成员观察。回归保持房间已同步、updater 未刷新，在认领等待锁时投递同 ID 截止收紧，确认释放锁后不会按旧截止认领。
- 截止证据通知不能只在长轮询等待分支消费。本地撤下与完整刷新共用锁内名册提交点：本地仅校准已观察项并发布 `CallMembers`，不启动后端配置或密钥分发；完整刷新在 `set_members` 前按最新 sticky 证据重验候选名单，后端需求和后续密钥分发的初始目标从实际提交的名单派生。已进入设备查询的发送仍持有旧目标副本，名册撤下不保证阻止尚未提交的媒体密钥发送；发送前重验是独立的媒体侧边界，不纳入上述两项 TTL 验收。名册回归分别持住 limited sync 后的 `/members`，以及暂停在 roster 已选出、尚未提交的位置；投递 E 的零 TTL 校准后，前者须在 HTTP 未返回时发布撤下，两者放行旧刷新后都不能让 E 复活。
- 过期赢家的排序目前也会拒绝此前未见、duration 更短的真实新 join。以上缺口来自静态复核，尚无运行回归。
- SDK 按键合并与通话名册的同键替换都可能丢掉旧代次的退场证据。SDK 响应回归需覆盖旧 join 只在独立轮询名册、SDK 同批收到退场及同键 rejoin 的顺序，分别使用 key-only tombstone 和 `LeaveOut::for_wire` 生成的显式离会。通话仍负责校验退场语义与信任。回归须核对旧代次的服务器退场时间，并在新代次未被观察且已过期后验证容差内外的结束候选，不能仅凭活跃新代次拒绝更早的 end。旧代次已过期时也要校验退场事件的设备：只有同一认证设备的退场能收紧服务器时间，未认证或错设备的事件不能借排序清理生成退场证据。以上缺口已静态核对，尚无运行回归。
